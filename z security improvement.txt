Based on an analysis of the backend employee registration flow (primarily in [employees.service.ts](file:///d:/source_codes/school_clocking_system/backend/src/modules/employees/employees.service.ts#L328-L435) and [create-employee.dto.ts](file:///d:/source_codes/school_clocking_system/backend/src/modules/employees/dto/create-employee.dto.ts)), here are the key issues and bugs:

### 1. Missing Cross-Tenant Validation (Security Risk)
When an admin registers an employee, they provide a `branchId`, `shiftId`, and optional `departmentId` in the request payload. However, the backend **does not validate** whether these referenced entities actually belong to the admin's school (`tenantId`). 
* **The Bug:** An admin could technically pass a `branchId` or `shiftId` belonging to a completely different school, linking the new employee to resources they shouldn't have access to, causing cross-tenant data contamination.

### 2. Global / Orphaned Employees for Super Admins
The `CreateEmployeeDto` payload does not accept a `tenantId` or `schoolId`. It relies entirely on the `TenantSubscriber` and `tenantLocalStorage` context of the logged-in user.
* **The Bug:** If a global SaaS Super Admin (who has no bound `tenantId`) attempts to register an employee, `tenantLocalStorage.getStore()` will return `null`. The employee and their user record will be saved with a `null` tenant ID, resulting in "orphaned" or global employees that do not belong to any school.

### 3. Lack of Role Escalation Prevention
The controller allows the creator of the employee to specify any `UserRole` (e.g., `role?: UserRole` in the DTO, defaulting to `employee`).
* **The Bug:** There is no check to prevent a regular school admin (or supervisor) from creating a user with a higher privilege role (like `super_admin` or `hr_admin`) if they have the `employees.create` permission. 

### 4. Unhandled Database Exceptions on Unique Constraints (e.g. Phone Numbers)
The database has a `unique` constraint on user phone numbers. However, during registration, `createEmployeeWithUser` only checks if the `username` is already in use. 
* **The Bug:** If an admin attempts to register an employee using a phone number that already exists in the system for another user, it will trigger an unhandled database exception (500 Internal Server Error) instead of a clean, user-friendly `ConflictException` (409 Conflict).
